01 / GAME LOOP

狙う前に、
考える。

エイムの技術だけで勝敗が決まらないよう、ダーツ盤の数字と残りスコアから次の一投を選ぶ判断を組み込みました。

照準を合わせる短い緊張と、命中した瞬間の強いフィードバックを繰り返し、 計算が得意でなくてもプレイを続ける中で選択肢を理解できる構造を目指しました。

INPUT

直感的に狙える操作

操作説明より先に触れることを優先し、照準と投擲の関係を単純化しました。

FEEDBACK

結果を一瞬で理解させる

得点、コンボ、残り投数を同じ視線の流れに置き、ヒット時の演出を集中させました。

REPLAY

他者のスコアを次の目標に

UGSランキングを導入し、一回の結果を次のプレイ理由へ接続しました。

02 / UI ARCHITECTURE

画面を増やしても、
修正箇所を迷わない。

遊び方、ランキング、リザルトをBuilderクラスへ分け、ランタイムでUIを構築しました。

画面ごとの生成責務を分け、色やレイアウトの設定場所を揃えることで、 修正時にシーン上の多数のオブジェクトを探す状態を避けることを狙いました。

  • BUILDERSHowToPlay / Ranking / NewRecord / Resultの各パネルを分離
  • ORDERDefaultExecutionOrderとAwakeを使い、利用側より先に生成
  • MOTIONDOTweenのSequenceで画面遷移と結果表示のテンポを統一
  • ONLINEUGSのスコア送信・取得を非同期で処理し、ニューレコード表示と連携
03 / LEARNING

設計の意図まで、
説明できるようにする。

動的UI生成は変更箇所を集約できた一方、視覚的な調整をコードだけで行うコストも生まれました。

今後は、頻繁に調整する値をScriptableObjectや設定アセットへ分離し、 コードによる構造の安全性と、エディタ上での調整速度の両方を取れる構成を比較検証します。
